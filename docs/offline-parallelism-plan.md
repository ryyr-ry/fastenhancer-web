# 長時間音声ファイルの並列処理：調査と実装計画

2026-10-12。実装前の `main`（`dedc8b9`）を対象とした調査記録です。以下の「現在」「提案」「未実装」は調査時点を指します。その後、左右・レート変換・WAVの逐次入出力・履歴を保持する内部SIMD並列化を実装しました。[現在の仕様・性能・配布方法](offline-parallel-processing.md)をご参照ください。調査用の試作はチェックアウト外に保存しています。

## 結論

並列処理を追加する価値があります。最初に実装するべきなのは、各チャンネルの履歴を保った左右の並列処理と、独立した出力サンプルを計算するサンプルレート変換の並列処理です。両方とも、試作で既存出力と全Float32サンプルが一致しました。

長いモノラル48 kHzにも複数コアを使うには、エンジン内部の処理を分解する追加段階が必要です。時間方向に区切って独立したエンジンを起動する方式は、2〜4秒の事前入力を加えてもGRUの履歴の差が残りました。既定の高速化として採用する根拠はありません。

処理速度と同時に、全ファイルを何重にも保持するメモリ構成を見直します。ステレオ48 kHz・1時間のFloat32 PCMは、1組だけでも約1.38 GBです。大量のWorkerに全ファイルを複製する実装は避けるべきです。

## 現在の処理と時間がかかる理由

現在の経路は次のとおりです。

```text
ファイル全体を読む → WAV / ブラウザのコーデックで全体をデコード
  → ブラウザではPCMのコピーを1つのmodule Workerに転送
    → 全体を48 kHzに変換
    → 左右を同じスレッドで、512サンプルずつ順番に推論
    → STFTの遅延を排出・除去
    → 元のレート・サンプル数へ変換
  → 呼び出し元で全体をPCM16 WAVへエンコード
```

- `src/api/enhance.ts` は1ジョブにつき1つのWorkerを作ります。UIを処理から分離していますが、1ファイルの計算を複数コアに分配していません。
- `src/api/channel-denoiser.ts` の左右処理は同期的な `map` です。`Promise.all` に置き換えるだけでは別スレッドの計算になりません。
- Nodeの `enhanceFile` は現在Worker threadsを起動せず、協調的に制御を戻す同じインライン処理を使います。
- `resamplePcm` は出力サンプルごとに窓付きsincの `sin` / `cos` を計算し、左右でも同じ係数をもう一度計算します。
- 48 kHzから48 kHzでも入力・最終出力をコピーします。推論ではフレームごとに出力配列を作り、その内容をファイル全体の出力へコピーします。
- WAVのデコード・エンコードは呼び出し元で同期処理します。長いファイルでは推論以外の段階でも待ち時間・UIの停止が生じます。

オフライン処理は実時間の再生速度を待つ設計ではありません。ただし、計算量は音声時間に比例します。現在の16 msごとのyieldは応答性のためのものであり、並列化ではありません。

## 実測：履歴を保持した左右の並列処理

環境はNode 24.19.0、AMD EPYC 9V45、SIMD、論理CPUの表示5、cgroupのCPU割当4コアです。リポジトリの異なるノイズ条件の音声を左右に配置し、16秒のステレオを処理しました。元のインライン処理と、各チャンネルの全フレームを1つのWorker threadで順番に処理する試作を比較しています。

Nodeの処理時間はウォームアップ後の値です。並列処理は2回の平均で、転送・結果の受信を含みます。プール起動は別計測で約23〜35 msでした。デコード・WAVエンコードはこの表に含めません。

| モデル | 入力レート | 現在の1スレッド | 左右2スレッド | 速度比 | 出力の最大差 |
|---|---:|---:|---:|---:|---:|
| Base | 48 kHz | 3.964秒 | 1.994秒 | 1.99倍 | 0 |
| Base | 44.1 kHz | 7.462秒 | 3.784秒 | 1.97倍 | 0 |
| Small | 48 kHz | 9.200秒 | 4.640秒 | 1.98倍 | 0 |
| Small | 44.1 kHz | 12.666秒 | 6.628秒 | 1.91倍 | 0 |

Chromium 154でも、既存のブラウザmodule Workerを2つ起動する方法を確認しました。16秒・48 kHzのステレオで、Baseは4.441秒→2.428秒（1.83倍）、Smallは9.850秒→5.214秒（1.89倍）でした。全サンプルが一致しています。この測定は新規Workerの起動を含む1回の比較で、Nodeのウォームアップ後の測定とは条件が異なります。

ブラウザの `crossOriginIsolated` はfalseでした。左右の並列化にはSharedArrayBufferやCOOP/COEPの追加が不要です。端末のCPU割当・発熱・他の処理により速度比は変わるため、実機の保証値ではありません。

## 実測：サンプルレート変換

上記44.1 kHzの処理では、往復のレート変換がBaseの約47%、Smallの約28%を占めました。16秒ステレオの往復で約3.5秒です。推論だけを速くすると、この部分がさらに目立ちます。

試作では、左右の係数計算を共有し、出力サンプルの区間ごとに計算を分配しました。1区間は65,536出力サンプルで、Worker数と区間の切り方を独立させています。

| 変換 | 現在 | 係数を左右で共有・1スレッド | 共有＋2スレッド | 共有＋4スレッド |
|---|---:|---:|---:|---:|
| 44.1→48 kHz | 1.751秒 | 0.848秒 | 0.442秒 | 0.242秒 |
| 48→44.1 kHz | 1.841秒 | 0.864秒 | 0.471秒 | 0.260秒 |

並列値は2回の平均で、タイルのコピー・転送・組み立てを含みます。プール起動の約20〜30 msは別計測です。全サンプルが一致しました。改善は係数の計算を共有する効果と、複数コアを使う効果の両方です。

互換性の要点は次のとおりです。

1. 出力位置 `i` はファイル全体の位置とし、現行と同じ `i * ratio` から入力位置を計算します。タイルごとに位相を0へ戻しません。
2. 入力はフィルタ半径分の前後を含めて渡します。タイル端をファイル端として扱いません。
3. 各サンプルの加算順序と、ファイル端の係数の正規化を維持します。
4. 同じレートは変換せず、現在と同じ値を返す専用経路にします。
5. 最終段では現在と同じ元のサンプル数を指定します。

8 / 16 / 22.05 / 44.1 / 48 / 96 / 192 kHz、双方向、モノラル／ステレオ、長さ1 / 513 / 1703サンプルの84入力条件を、3種類の分割幅で確認しました。252ケースすべてで全Float32サンプルが一致しました。これは試作の数値比較であり、製品のキャンセル・進捗・CSPまで検証した結果ではありません。

係数の位相テーブル化や別のリサンプラーへの置換は、さらに速くなる可能性がありますが、丸めやフィルタ特性が変わります。最初の実装では上記の計算共有と独立した出力位置の分配を優先します。

## 時間方向の分割を既定にできない理由

`FeState.gru_h` はフレーム間で保持されます。GRUは前の隠れ状態を使う非線形な更新であり、STFTの1024サンプルだけが履歴の範囲ではありません。重みから「直前2秒だけあれば一括処理と同じ」とは保証できません。

実際の音声16秒を一括処理し、8秒の位置から新しいエンジンで後半を処理する試作と比較しました。境界は512サンプルの整数倍です。後半の前に事前入力を加え、その出力を捨ててから比較しています。

| モデル | 事前入力 | 後半8秒の最大絶対差 | 後半8秒の差のRMS | 冒頭1秒を除いた差のRMS |
|---|---:|---:|---:|---:|
| Base | 0秒 | 0.1736 | 0.00791 | 0.00509 |
| Base | 約2秒 | 0.0720 | 0.00304 | 0.00297 |
| Base | 4秒 | 0.0364 | 0.00204 | 0.00197 |
| Small | 0秒 | 0.1142 | 0.01211 | 0.00971 |
| Small | 約2秒 | 0.0811 | 0.00812 | 0.00595 |
| Small | 4秒 | 0.0510 | 0.00437 | 0.00346 |

元の8秒の履歴をすべて再処理した場合だけ、今回の比較では差がゼロになりました。これは試作の位置合わせを確かめる対照実験でもあります。波形差の測定であり、PESQ・STOI・聴取による品質評価ではありませんが、短い事前入力で既存出力を保てるという仮定は成立していません。

クロスフェードで隠せるのは切り替えの境界です。その後も続く隠れ状態の違いは解消しません。無音で分割する案も、現在のエンジンが無音中に状態を自動リセットしないため、一括処理と同じにはなりません。

別の対照実験では、履歴をすべて与えても、区間末尾を即座にゼロ埋めすると最後の512サンプルに差が出ました。次の実入力512サンプルを含めて処理し、必要な出力だけを切り出すと差がゼロになります。現行の遅延除去とSTFTの合成を考慮する必要があります。ゼロ埋めは本当のファイル末尾だけです。

正確な状態をチェックポイントへ保存する案は、再開や再処理には使えます。現在の `fe_process_frame` で全チェックポイントを作るなら、先に全推論を順番に実行するため、初回ファイル処理の高速化にはなりません。Decoderなどの不要な段階を省いた状態専用の計算を追加する案は別の内部改修です。直列の事前計算と再処理の費用を含めて測定する必要があり、単に状態を保存すれば速くなるとは扱いません。

時間分割は将来の品質評価用の実験として分離します。採用する場合も明示的な別モードとし、区間幅・前後の入力・左右共通の重みの和が1になるクロスフェード・全体のレート変換位相を固定する必要があります。現在の測定だけで既定の区間幅や事前入力秒数を決めるべきではありません。

## APIと実装の境界

最初の提案は、既存のオプションに次を追加する形です。

```ts
// 提案。現行のAPIにはまだ存在しません。
parallel?: false | { maxWorkers?: number };

const cleanWav = await enhanceAudio(file, {
  parallel: { maxWorkers: 4 },
  signal,
  onProgress,
});
```

`maxWorkers` はジョブ全体の上限であり、各チャンネルに4つずつWorkerを作る指定ではありません。最初の段階では推論の並列数はモノラル1・ステレオ2です。レート変換は、十分長い入力ならその上限まで分配します。モノラル48 kHzで4倍になることは、この段階では期待できません。

- 既定は従来の処理経路を維持します。高速化は明示的なオプションで追加し、既定を変更する判断は回帰検証と実機測定の後に行います。
- `worker: false` はWorkerを起動しない契約を維持します。並列指定との同時使用は明確なValidationErrorにします。
- ブラウザはmodule Worker、Nodeのファイルアダプターは遅延ロードするWorker threadsを使います。ブラウザ向けの入口へ `node:` の依存を混入させません。Bunは対応を実測してから有効にします。
- 全ファイルを各Workerへ送りません。各チャンネルの必要範囲、または変換タイルとその前後だけを、内部で所有する転送用バッファとして渡します。呼び出し元のバッファをdetachしません。
- モデルとコンパイル結果はプール内で再利用します。タイルごとにロード・コンパイルしません。コンパイルした `WebAssembly.Module` のstructured cloneを使う場合も、各エンジンのWASMメモリと状態は独立させます。ModuleはArrayBufferと同じ転送用リストへ入れる対象ではありません。
- 推論を入力ブロックで渡す場合も、チャンネルを同じWorkerに固定し、同じエンジンの状態を順番に更新します。ブロック境界でreset・遅延除去・ゼロ排出を繰り返しません。
- オフライン処理の自動バイパスは追加しません。負荷が高くても、途中を未処理音に変えずに処理します。

スケジューラーは、同一プール内でWorkerが同時に複数ジョブを受けないようにします。キャンセル・1つのWorkerの失敗・進捗コールバックの例外では、残りの仕事も止め、待機中のPromiseをすべて終了させます。ジョブIDと世代で、停止したジョブの遅い通知を次のジョブへ混ぜません。

同時に複数ファイルを処理する場合も、各ファイルが独立した最大数のプールを作る構成を避け、全体のCPU・メモリ上限を共有します。`hardwareConcurrency` は参考値です。今回も表示は5・CPU割当は4でした。既定の上限は主スレッドとリアルタイム音声の余裕を残し、端末・入力サイズから制限します。小さなファイルや1コア環境では並列化を省く判断も必要です。

進捗は完成した有用なサンプル数と段階で集計し、現在の0〜1・単調増加の契約を維持します。先に完成したタイルから通知しても、結果は入力位置順に組み立てます。デコード・モデル読み込み・エンコード・保存の時間も扱い、内部計算が終わっただけで保存まで完了した表示にしません。

## 長時間録音のメモリ対策

現在の入力、Worker用コピー、48 kHzの入力、推論結果、最終レートへのコピー、WAVバイト列は、複数が同時に残る可能性があります。実際のピークはGC・形式・レートで異なりますが、数GBになり得ます。並列化でこの問題を増幅しない設計が必要です。

1. Worker内で所有する48 kHz入力は不要な再コピーを避けます。最終レートが48 kHzなら、内部の新しい推論結果をそのまま返し、もう1組コピーしません。公開APIの入力保護を維持します。
2. Workerへの送信・未完成の結果は個数に上限を設けます。ファイル全体の全タイルを先に生成してキューへ入れません。
3. WAVはヘッダーを読み、順次デコード・変換・推論・エンコードするアダプターを追加します。左右は独立した状態を維持し、必要なフィルタの前後と未排出のSTFT出力だけを保持します。
4. Nodeの保存は現在と同じ一時ファイル＋成功時のrenameとし、中止や失敗で既存の出力を壊しません。読み書きのストリームを閉じてから置換します。
5. ブラウザのBlobを返すAPIでは、最終出力のサイズ自体は残ります。さらに長い録音向けには、ReadableStreamやファイル保存先へ書き出す別の入口が必要です。

逐次処理の段階では、次の入力タイルの変換、現在のタイルの左右推論、前のタイルの最終レート変換・書き出しを重ねるパイプラインも検討します。各段階が別々の最大数のWorkerを作る構成にはせず、同じ上限の中で配分します。推論Workerに渡すチャンネルの状態と順序は固定し、前後が必要なリサンプラーは隣接データがそろってから確定した範囲だけを出します。未処理タイルと完了待ちの出力に上限を設け、書き出しが遅ければ入力を止めます。

圧縮音声は `decodeAudioData` が現在全体をデコードします。推論Workerを増やしても、この段階のメモリや中断できないコーデック呼び出しは解決しません。まずWAVで長時間処理を完成させ、圧縮形式のストリーミングはdemux・タイムスタンプ・デコーダーのflushを含む別段階として扱います。

## モノラルも多コア化するエンジンの追加段階

このモデルのGRUは、時間方向には依存しますが、各RNNFormerブロックの周波数位置ごとに独立しています。Baseは36、Smallは48の周波数位置です。Attentionは現在のフレームの周波数間を混ぜるため、GRUの更新を完了してから計算する必要があります。

履歴を保った並列化の候補は、少数フレームのバッチを次の順に処理する方式です。

```text
入力タイル → STFT・Encoder・PreNetをフレームごとに並列計算
  → GRU block 0：周波数位置を分配し、各位置では時間順に全バッチを処理
  → 全位置の完了を待ち、Attentionをフレーム／出力行ごとに並列計算
  → GRU block 1、block 2でも同じ順序を守る
  → PostNet・Decoder・iFFTをフレームごとに並列計算
  → overlap-addを元の順序で合成し、次のタイルへ状態を引き継ぐ
```

各周波数位置のGRUは同じ順序で状態を更新します。加算の順序が変わる並列reductionを避け、既存と同じSIMD計算を使うことを出力比較で確認します。全ファイルの中間テンソルを保持せず、例えば64フレーム程度のタイルを使って通信と同期をまとめます。64フレームは候補であり、速度・メモリ測定で決めます。

ここは既存WASMの外側へWorkerを増やすだけでは実現しません。現在のステージ関数は内部のstatic関数で、1フレーム用の作業領域を再利用します。バッチの作業領域、周波数ごとの隠れ状態の所有、ステージの入口、同期を追加する必要があります。

最初の検証はオフライン専用の追加バイナリ・内部APIに限定し、既存のリアルタイムWASM・Workletを維持します。通常のmodule Worker間でタイルを転送する方式ならCOOP/COEPなしで動かせますが、転送量と同期の費用を実測する必要があります。shared-memory / pthreads版は追加の高速経路として検討します。ブラウザではクロスオリジン分離の要件があるため、現在のデモや埋め込み先に必須化しません。

実装前にステージごとの計算時間を測り、バッチ版1スレッドが従来と同じ出力になることを確認し、その後に2 / 4スレッドを比較します。この新エンジンの速度向上はまだ測定しておらず、4倍などの保証はできません。

## 実装順序と完了条件

| 順序 | 変更 | 完了条件 |
|---|---|---|
| 1 | オプション、上限付きプール、左右を同じWorkerに固定する処理 | 全3モデル・scalar/SIMD・1/2チャンネルで従来出力と一致。キャンセル・失敗の後も次のジョブが成功 |
| 2 | 係数の計算共有、全体位置を使う変換タイル、不要な内部コピーの削減 | 対応レート範囲の代表値・端点、末尾・短い入力・元のサンプル数を検証。端末ごとの速度とピークメモリを確認 |
| 3 | WAVの逐次入出力とバックプレッシャー | 長時間録音でも作業メモリが時間に比例して増えない。Nodeの置換・中止・同一入出力パスの契約を維持 |
| 4 | オフライン専用のバッチ処理と内部並列化 | 1スレッドの数値互換を先に確立。2/4スレッドで効果を確認し、対応しない環境では既存経路を利用 |
| 別枠 | 品質を変え得る時間方向の分割 | 長い実音声、ノイズ変化、声の途中の境界、無音、ステレオで品質・聴取を評価してから採否を判断 |

回帰検証では、空入力、1 / 511 / 512 / 513サンプル、長さの不一致、NaN/Inf、片側無音、左右同一、異なるノイズ条件、遅延の排出、レート変換端のインパルス、並列数によらない出力、入力バッファの保護を確認します。

実際に複数Workerが同時に働くこと、キューの上限、起動中・変換中・推論中・エンコード中の中止、Worker起動の失敗、途中の異常終了、古い進捗通知、コールバックの例外、複数ファイルの公平性も確認します。CSP、自前配信、Viteの本番バンドル、Node、Bun、Chromium / Firefox / Safariの検証を含めます。

この調査で確認したブラウザはChromiumだけです。エンジン内部の並列化、ストリーミング入出力、製品APIの回帰・異常系検証は未実施です。現在の既存テストの通過件数を、新機能の検証件数として扱いません。
